# Apna Campus backend audit

Audit date: 2026-10-22

## Canonical architecture

The canonical backend is `backend/`: NestJS controllers and services with Prisma Client. The user selected MongoDB Atlas as the target database. `backend/prisma/schema.prisma` has now been converted offline to Prisma's MongoDB provider; SQL files in `backend/prisma/migrations` remain historical PostgreSQL artifacts and are not applied to Atlas. `frontend/src/services/api.js` targets the API at `VITE_API_URL` (defaulting to localhost in development). `ai_service/` is a separate FastAPI service used by hostel complaint triage.

The root `prisma/schema.prisma` remains a divergent PostgreSQL schema copy and is not used by the backend package scripts. Treat it as legacy; do not run Prisma commands against it. `server/` is a separate Express demonstration API. Its user list is now empty and its Campus Connect state is held in process memory. It is not suitable as the canonical persistence layer.

## Role inventory

The Prisma `Role` enum includes `SUPER_ADMIN`, `MANAGEMENT`, `PRINCIPAL`, `ADMIN`, `HOD`, `FACULTY`, `STUDENT`, `EXAM_CELL`, `ACCOUNTS`, `LIBRARY`, `PLACEMENT`, `TRANSPORT`, `HOSTEL`, `STAFF`, `WARDEN`, `CANTEEN`, `ADMISSIONS`, `MAINTENANCE`, and `NON_TEACHING`. Frontend portal components also include these operational roles. Existing RBAC policies cover the role set, but endpoint enforcement and department/ownership scoping have not yet been verified as a whole.

Role scope expected by the current policy design:

| Role group | Expected scope | Typical permitted data |
|---|---|---|
| Super Admin | System | User/role configuration, audit and system controls |
| Management, Principal | College | Institution-wide summaries and designated approvals |
| Admin | College operations | Student/faculty records, configuration and operational workflows |
| HOD | Department | Department students/faculty, academic moderation and approvals |
| Faculty | Assigned department/classes | Assigned students, attendance and marks entry |
| Student | Own record | Own profile, academics, fees, hostel and service requests |
| Accounts, Exam Cell, Admissions | Functional module | Finance, examination, or applicant records respectively |
| Library, Placement, Transport, Hostel/Warden, Canteen, Staff/Maintenance, Non-teaching | Functional module | The service records represented by each portal |

This matrix is a baseline for enforcement, not a claim that existing routes already implement every row. Only verified JWT identity can be used for authorization; a body/query/header role or user ID is not identity.

## Initial concrete defects and risks

- `render.yaml` previously used `prisma migrate deploy || true`, allowing deployment to start after a failed required migration. The command now fails closed.
- NestJS CORS previously allowed every origin after explicit checks. It now allows only local development origins and comma-separated `CLIENT_URL` entries.
- The global exception filter previously returned raw non-HTTP exception messages. It now returns a generic server error for unhandled exceptions.
- Canteen routes now require an existing JWT identity and enforce role scopes. Orders derive the student from that identity, calculate prices from the database menu, conditionally debit the wallet, and create the order in one transaction. Invalid order-state transitions are rejected. The canteen staff frontend now reads and updates real menu/order rows and no longer adds seeded revenue to its displayed total.
- Fee endpoints require JWTs; sensitive financial reads and writes enforce role checks, and student proof submissions/documents use the JWT-linked student. Student statement routes fail honestly with `503` until fee assessments exist. The student proof-history and attachment routes are ownership-scoped. Accounts queue responses omit file bytes and internal student IDs.
- Dependencies were absent at the beginning of implementation; a later `npm ci` completed for root and backend, and frontend dependencies are installed. No lockfile changes were needed.
- Root and backend Prisma schemas differ; migrations have not been applied to any database during this audit.
- `backend/.env` is configured privately for the verified development-only Atlas database `apna_campus_dev`; never copy its URI into source control or documentation. The safe `.env.example` documents the URI format.
- The backend schema uses Prisma's MongoDB provider and retains historical PostgreSQL migration files as unapplied artifacts. `prisma db push` is the explicit schema-sync mechanism; deployment does not run it automatically.
- Render no longer provisions its own PostgreSQL database or runs a schema change at startup. Atlas `db push` is explicit through `prisma:db-push`; use only after reviewing the schema diff and confirming the target is safe.
- Hostel reads no longer insert example hostels/rooms into an empty database. The residence endpoint no longer defaults a missing identity to roll `01` or returns fabricated roommates; it now returns the student's persisted residence data and roommates, or a not-found response. This flow has not been integration-tested against a database.
- Hostel allocation, transfer, and vacate update student residence, room occupancy, and deterministic active bed claims in one transaction. Room updates compare current capacity/occupancy, student writes compare the previously observed allocation, and duplicate active beds conflict. New Student housing fields no longer default to a sample hostel/room. The 2026-10-22 aggregate review found zero students with the audited sample housing values.
- Hostel dashboard capacity is calculated from `HostelRoom` rows because denormalized `Hostel` totals are not maintained by allocation writes. Staff-only role gates protect hostel inventory/dashboard and visitor operations. Student complaint, gate-pass, and document access is restricted to the JWT-linked user; complaint and pass submissions resolve their owner and residence from the database. Gate-pass transitions are sequential compare-and-set updates and no longer claim unverified parent/mentor clearance or issue a pretend-valid QR value.
- The student hostel UI no longer starts with fabricated resident complaints, room/fee claims, staff assignments, or submission success. Residence, complaint, and gate-pass views now load authenticated API data; gate-pass creation and Warden lifecycle decisions use the backend. The UI does not claim mentor/parent verification or a biometric QR integration that is not implemented.
- Admin metrics now use actual counts without substituting demonstration numbers, report unsupported measures as `null`, and probe MongoDB using a ping command. The diagnostics output no longer claims every route is guarded or that an audit stream is append-only. This change has not been typechecked.
- Other demo or incomplete behavior remains, including several portal-local stores, some faculty/admin dashboards, and unimplemented backup/email/telemetry integrations. Those values must not be presented as live persisted data.
- The report student roster now returns only Prisma query results; empty data stays empty and database errors propagate instead of generating a synthetic roster. The admin complaints UI no longer starts with fake complaint/staff records, calls the AI service directly from the browser, claims an assignment succeeded when its API write fails, or displays synthetic model scores. It shows loading, empty, and load-error states. Integration with a running AI service has not been verified.
- AI evaluation metrics are fetched server-side from `${AI_SERVICE_URL}/metrics` through `GET /api/admin/ai-metrics`. The route is JWT protected and restricted to Super Admin, Management, Principal, and Admin. The UI displays metadata served by FastAPI, including its synthetic-data notice; the endpoint has not been exercised against a running AI service.
- Administrative backup listing/creation/restore no longer returns fabricated SQL snapshots or success responses; it returns 503 until a real backup provider is configured. The integration list no longer claims SMTP, SMS, payments, object storage, or biometric systems are operational without configured clients. The configured AI service can be health checked. Admin approvals and settings now use `WorkflowRequest` and `SystemSetting` records with audit writes; persisted RBAC configuration is not yet wired into runtime route guards.
- Admin and self-service password-reset routes return 503 until an email delivery provider exists. Reset tokens are no longer returned directly by these endpoints.
- Admission enrollment no longer returns an account activation token in the admin response. The newly provisioned student account stays unactivated and the UI clearly reports that invitation delivery is pending provider configuration.
- The Accounts student roster now reads the JWT-protected backend student endpoint. The roster no longer calculates fee statuses from roll-number arithmetic or exports invented balances; statements/defaulter reports indicate unavailable assessment data. Counter receipt inputs no longer start with sample student/payment values.
- Student fee UI no longer shows hardcoded historical dues, receipts, fake UPI QR/bank instructions, or simulated payment success. Students can list their persisted proof submissions and retrieve their own proof attachment; the generated proof PDF is explicitly a submission summary, not a receipt. Official assessments/statements remain unavailable.
